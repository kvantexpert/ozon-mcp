Текущий HEAD на момент аудита: `265aeeb78ce5bf043d54051776084e6203bcc32e`.

## 2. Архитектурный результат

В репозитории нет собственного кода реализации Ozon API: production runtime запускает upstream-пакет:

`ozon-mcp-ru==0.6.0` → `marketplaces-mcp-ru==0.6.1`.

Рабочий VPS ранее проверен на byte-for-byte совпадение установленного `marketplaces-mcp-ru 0.6.1` с upstream commit `ec2114595695536e001e09e1144a357118852db1`.

Следовательно, основной риск текущего проекта находится не в локальном API-коде, а в:

1. актуальности upstream;
2. корректности MCP operation catalog/schema;
3. правильном формировании Ozon payload;
4. доступности категории для конкретного кабинета;
5. актуальности проектной документации.

## 3. Сверка импорта с Ozon API

Используемый endpoint:

`POST /v3/product/import`

подтверждён как метод создания/обновления товара. Максимум — 100 товаров в одном запросе, ответ содержит `task_id`; результат нужно проверять через `POST /v1/product/import/info`.

Актуальная схема требует не только `offer_id`, `attributes`, `images`, размеры и `type_id`. Для создания товара критичны также:

- `description_category_id` — обязательный идентификатор категории;
- `type_id` — обязательный идентификатор типа;
- `offer_id` — обязательный артикул продавца;
- `price` — обязательная цена;
- габариты/вес: `depth`, `width`, `height`, `dimension_unit`, `weight`, `weight_unit`;
- `currency_code` должен соответствовать валюте кабинета.

Ozon отдельно указывает, что реальные объёмно-весовые характеристики нельзя пропускать или передавать нулевыми.

### Важное исправление проектной документации

Ранее в проекте контракт был сокращён до:

`{items:[{offer_id, attributes, images, dimensions, type_id}]}`

Это недостаточно как описание реального Ozon request schema.

MCP `describe_method` показывает упрощённый внутренний контракт operation wrapper, а не полную актуальную схему Seller API. При формировании реального payload ориентироваться нужно на фактическую схему Ozon, а не на сокращённое описание wrapper.

Также `dimensions` не следует считать самостоятельным полем Ozon API: для `/v3/product/import` используются отдельные поля `depth/width/height/dimension_unit/weight/weight_unit`.

## 4. Фактический тест категории 24.09.2026

Для нового Ozon-аккаунта проверена категория:

- `description_category_id=200001489` — «Цифровые товары»;
- `type_id=971075562` — «Код активации офисного приложения».

Результат дерева категорий нового аккаунта:

- `200001489` имеет `disabled=true`;
- дочерний `971075562` также имеет `disabled=true`;
- полный доступный через API category tree на этом аккаунте также возвращал категории/types как disabled.

Попытка создания товара через `/v3/product/import` дала:

1. без `description_category_id` → `description_category_is_empty`;
2. с `description_category_id=200001489` → `used_forbidden_category`.

Вывод: текущая причина невозможности массовой загрузки — доступность категории в новом кабинете, а не лимит 293 товаров и не размер партии.

До появления доступной категории повторять 293 импорта бессмысленно.

## 5. Новый аккаунт и лимиты

Фактический ответ `/v4/product/info/limit`:

- total: `0 / 500`;
- daily_create: `2 / 1500`;
- daily_update: `0 / 20000`;
- rate limit: `30000/min`.

Поэтому утверждение «лимиты позволяют загрузить 293» остаётся верным, но документация должна хранить фактическое `daily_create=2`, а не старое `0`.

`daily_create.usage=2` не означает наличие двух созданных товаров: `/v3/product/list` на новом аккаунте вернул `total=0`.

## 6. Точный каталог 293

Целевой набор остаётся неизменным:

- `00000002` — 193;
- `00000003` — 100;
- всего 293.

Дополнительные группы:

- `00000292` — 28;
- `00000296` — 4;
- `00000314` — 2;

в импорт не входят.

Партии: 100 + 100 + 93.

`GOODS.JSON` не изменять.

## 7. Цена

Зафиксировано правило:

`00001 → 00003 → 00004`.

Это внутреннее правило проекта, полученное из данных GOODS.JSON. Его нельзя выдавать за правило Ozon API.

При этом цена обязательна в реальном `/v3/product/import`, поэтому правило цены должно использоваться при фактическом построении каждого item.

## 8. Варианты товаров

Basic / ПРОФ / КОРП, электронная / коробочная поставка, количество пользователей и другие варианты остаются отдельными предложениями.

Не использовать `9048` для искусственного объединения всех вариантов. Ozon описывает `9048` как механизм объединения карточек при совпадении остальных характеристик и наличии различающихся вариационных характеристик.

Для текущей задачи безопасное правило: не объединять 293 позиции автоматически.

## 9. Атрибуты

Подтверждено:

- `8229` — «Тип»;
- `971075562` — «Код активации офисного приложения».

Нельзя угадывать dictionary value для `8229`.

Ранее полученный dictionary lookup вернул:

- `971075556` — Код активации антивируса;
- `971075557` — Цифровой код активации ОС;
- `971075562` — Код активации офисного приложения.

Важно: наличие атрибута в category schema не означает, что категория разрешена конкретному кабинету.

## 10. Что найдено как ошибки/несоответствия

### A. Устаревший статус категории — ИСПРАВИТЬ
Документация называла `200001489` рабочей категорией, но 24.09.2026 новый аккаунт получил `disabled=true` и `used_forbidden_category`.

### B. Неполный import contract — ИСПРАВИТЬ
Документация описывала только wrapper-поля и не фиксировала обязательные `description_category_id`, `price`, реальные dimensions/weight.

### C. Неверное представление dimensions — ИСПРАВИТЬ
Не считать `dimensions` единым полем Ozon API. Нужны отдельные `depth/width/height/dimension_unit/weight/weight_unit`.

### D. Устаревший daily_create — ИСПРАВИТЬ
Документация содержит `0/1500`; фактически на тестах было `2/1500`.

### E. Несоответствие check_auth — ИСПРАВИТЬ
Фактический `ozon_check_auth` показывал `active_cabinet=null`, `source=env`, `cabinets=[]`. Поэтому нельзя писать, что активный кабинет «определяется окружением» как подтверждённый named cabinet.

### F. История тестов отстаёт от текущих тестов — ИСПРАВИТЬ
`TEST_HISTORY.md` заканчивался 22.09.2026 и не содержал двух сегодняшних импортных ошибок и полного category-tree результата.

### G. Не найден локальный production-код импорта
Репозиторий является deployment/documentation layer над upstream MCP. Поэтому исправление payload должно быть либо в вызывающем сценарии, либо в upstream operation schema, а не в несуществующем локальном `src/`.

## 11. Что подтверждает документация Ozon

Актуальная схема `/v3/product/import` подтверждает:

- до 100 товаров за запрос;
- асинхронный `task_id`;
- обязательные category/type/offer/price;
- обязательные реальные dimensions/weight;
- currency должна соответствовать настройке кабинета;
- обязательные attributes зависят от категории;
- после импорта результат проверяется через `/v1/product/import/info`.

Ozon также обновлял описание `/v3/product/import` 10.07.2026: `items.offer_id` был отмечен обязательным, а `items.images360` удалён из запроса.

Для category tree API возвращает флаг `disabled`; создавать товары можно только в разрешённых конечных категориях/types.

## 12. Решение после аудита

Не менять:

- `GOODS.JSON`;
- точный набор 293;
- правило цены;
- разделение вариантов.

Исправить документацию и считать текущим блокером:

**новый Ozon-аккаунт не имеет доступной для API категории 200001489 / type 971075562.**

Следующий импорт начинать только после того, как Ozon API для нового аккаунта вернёт нужную категорию/type без `disabled=true` и создание перестанет возвращать `used_forbidden_category`.

После разблокировки payload партии должен соответствовать полной схеме Ozon, а не сокращённому MCP wrapper description.
